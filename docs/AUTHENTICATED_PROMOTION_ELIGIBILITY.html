ODIN Authenticated Promotion Eligibility

Implemented locally; remote bootstrap requires the controlled ship gate.

What it proves

A manual, owner-dispatched workflow can bind one stage, demo, or production authorization to one immutable candidate SHA and one exact Trusted Validation evidence bundle.

Trust chain

  1. Require the exact owner login and numeric GitHub user ID.
  2. Observe a successful, first-attempt, manually dispatched Trusted Validation run.
  3. Download exactly one linked three-file evidence artifact and verify the canonical manifest SHA-256.
  4. Bind candidate, workflow, repository, run, action, nonce, authorization text, expiry, and environment approval into schema-valid records.
  5. Upload a five-file decision artifact with accessible HTML.

What it cannot do

It cannot build or publish a package, create a tag or release, deploy ODIN, mutate Kubernetes, change DNS/TLS, write secrets, reset demo data, or touch production.

Runner boundary

The workflow runs only on the established M4 self-hosted runner and executes reviewed owner-only code. It does not describe that runner as isolated. The eligibility job never checks out candidate content; it imports a fixed, hash-verified helper closure fetched from the workflow's own exact SHA.
