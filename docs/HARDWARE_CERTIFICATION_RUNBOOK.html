Hardware certification runbook

Operator workflow for Bambu, Moonraker, PrusaLink, and Elegoo. Replay, passive observation, and authorized exercise are deliberately separate claims.

Open the printed artifact and confirm it says SIMULATED REPLAY ONLY.

2 · Protect one target

Keep its JSON outside the repository and artifact tree. It must be current-user-owned, nonsymlink, mode 0400 or 0600, and use one private-resolving host.

Run openssl rand -hex 32 once per target and store the result as evidence_correlation_key. Reuse it only to prove that observe and exercise evidence concern the same target; rotate it to break that relationship. It is not a hardware identifier, and evidence retains only its domain-separated SHA-256.

3 · Passive observation

python3.11 -m ops.hardware_certification observe \
  --target-config /secure/operator/path/target.json

Evidence excludes endpoints, credentials, hardware IDs, topics, raw payloads, and filenames. Model identity must be device-reported; failed observations retain unknown, not the configured expectation. Elegoo identity comes from a separate unsolicited attributes frame correlated with two status frames. Moonraker and PrusaLink's documented allowlisted APIs do not expose printer model identity—PrusaLink's /api/version.printer is a software version—so both currently fail closed with model_identity_unavailable.

4 · Default-deny authorization

Use only .3mf for Bambu and .gcode for Moonraker or PrusaLink. PrusaLink .bgcode is not yet certified and is rejected.

python3.11 -m ops.hardware_certification authorize-template \
  --target-config /secure/operator/path/target.json \
  --actions upload,start,pause,resume,stop \
  --asset /secure/operator/path/disposable.3mf \
  --output /secure/operator/path/authorization.json

The operator must copy the challenge, affirm all three safety checks, and approve every action. Elegoo uses --elegoo-filename and retains only its salted hash.

5 · Authorized exercise

python3.11 -m ops.hardware_certification exercise \
  --target-config /secure/operator/path/target.json \
  --authorization /secure/operator/path/authorization.json \
  --ledger /secure/operator/path/used-nonces \
  --asset /secure/operator/path/disposable.3mf

The worker stops on the first receipt, state, or same-run identity mismatch. Setup, execution, cleanup, or interrupt failures after authorization consumption publish sanitized failure evidence.

6 · Verify identity and import

python3.11 -m ops.hardware_certification verify-artifact /secure/operator/path/bambu-observe --mode observe --protocol bambu --model-family X1C --firmware-version 01.08.00.00 --api-version unknown

make verify-edu-live HARDWARE_EVIDENCE_DIR=/secure/operator/path/verified-hardware HARDWARE_IDENTITY_FILE=/secure/operator/path/current-identities.json

Verification derives the current ODIN HEAD itself and has no caller override. Import also requires a separate protected mode-0600 identity file with current model, firmware, and API expectations for every supplied protocol. Only clean observe artifacts from the current commit and implementation that match those expectations populate live rows. Any age or identity drift becomes BLOCKED pending recapture.

7 · Telemetry V2 handoff

python3.11 -m ops.hardware_certification telemetry-prerequisites \
  --observe-artifact /secure/operator/path/bambu-observe \
  --exercise-artifact /secure/operator/path/bambu-exercise \
  --output /secure/operator/path/telemetry_v2_prerequisites.json

Only same-target, same-model live status, commands, and dispatch can map to pass. AMS remains blocked until ODIN's actual Telemetry V2 slot-synchronization path is directly observed; an ams_read action alone is insufficient. Database/alert transitions and the seven-day soak also remain blocked. No flag is changed.
