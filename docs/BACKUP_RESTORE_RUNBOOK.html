ODIN Backup and Restore Runbook

Verified application-managed backup and offline restore for SQLite and PostgreSQL 16.

Backups may contain student or customer data. Never email them; use approved encrypted storage.

Shared controls

  • All backup and restore actions require a superadmin.
  • Candidates are schema-allowlisted, restored for validation, and addressed by SHA-256.
  • Restore is offline: stop all ODIN API and worker roles before applying.
  • Record timings, size/hash, operator, outcome, recovery, and expiry—never row contents.

Use make test-database-parity CANDIDATE_PYTHON=python3.11 for measured HTML evidence.

SQLite

Backup

  1. Confirm free space (at least twice database size or 16 MiB).
  2. Create from System or POST /api/backups.
  3. Run:
make verify-backup DATABASE_URL=sqlite:////data/odin.db BACKUP_NAME=latest PYTHON=python3.11

Restore

  1. Upload through POST /api/backups/restore.
  2. Restart the bootstrap owner. ODIN locks, checkpoints WAL, journals a current rollback, and atomically swaps.
  3. Migrations and seed work run before finalization; failures and interrupted provisional restores roll back automatically.
  4. Verify readiness, login, inventory, jobs, and RBAC before reopening.

PostgreSQL identities

  • odin_admin: initialization-only superuser, secret visible only to PostgreSQL.
  • odin: application owner, no superuser/createdb/createrole.
  • odin_maintenance: non-superuser validation identity with CREATEDB; secret visible only to the bootstrap-owner API.
DATABASE_URL=postgresql://odin@postgres:5432/odin
DATABASE_MAINTENANCE_URL=postgresql://odin_maintenance@postgres:5432/postgres

PostgreSQL backup

  1. Create from System or POST /api/backups.
  2. ODIN dumps only the canonical public object allowlist and strips ownership, privileges, and comments.
  3. ODIN restores into a disposable database and validates exact schema before publication.
  4. Run make verify-backup with the credentialless application URL and mounted application/maintenance password files.

PostgreSQL restore

  1. Upload a canonical .dump and record candidate_sha256.
  2. Stop every ODIN role; leave PostgreSQL running. Isolate the target database network until verification completes; session checks are point-in-time and network quiescence is the operator's continuous exclusion boundary.
  3. Set ODIN_POSTGRES_RESTORE_ACKNOWLEDGEMENT to the exact SHA-256 and start only the bootstrap owner.
  4. ODIN locks, refuses all other target sessions, checks dependencies, then creates a current verified rollback.
  5. The allowlisted restore is transactional and object-scoped; bootstrap, validation, and auditing occur under the lock.
  6. Failures roll back immediately. A next start recovers any restore_in_progress interruption before serving.
  7. Remove the acknowledgement, start other roles, and verify readiness, login, RBAC, WebSocket, background writes, printers, and jobs.

Failure rules

  • Never edit a pending manifest to force startup.
  • Never put passwords in PostgreSQL URLs or PGPASSWORD.
  • Never bypass session refusal, checksums, TOC allowlists, or disposable validation.
  • If rollback fails, keep ODIN stopped, preserve evidence, and escalate—do not improvise restore flags.
