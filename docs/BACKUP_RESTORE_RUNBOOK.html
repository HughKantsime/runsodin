ODIN Backup and Restore Runbook

Verified application-managed backup and offline restore for SQLite and PostgreSQL 16.

Backups may contain student or customer data. Never email them; use approved encrypted storage.

Paid license identity and recovery

A device-v1 paid license requires both the original installation ID and the Ed25519 private device key. Hardware replacement works without a transfer when both are preserved. In the configured `LICENSE_DIR` (normally `/data`), preserve `.odin-install-id`, `.odin-device.key`, and `odin.license` together in a separate encrypted host/volume backup. Keep the private key readable only by the ODIN service account (`0600`); never paste it into a ticket, log, request code, or chat.

Application database backups, portable exports, and support bundles do **not** transfer a bound license. Do not add the private key to these artifacts. Stop ODIN before restoring its identity files, restore both identity files and the signed license to the configured license directory, preserve ownership and key permissions, then restart and verify Settings > License. Do not overwrite another running installation's identity: cloning the private key clones its identity.

Legacy paid licenses remain valid indefinitely under their original installation and expiry rules. Conversion is voluntary and applies to the whole purchase, including every grant. Coordinate installation owners before confirming conversion; previous offline legacy files cannot be revoked.

For a mismatch, first restore the original identity files. If the old key is available and you are transferring to a new identity, unactivate the old installation before activating the new one. For an offline transfer, generate the signed unactivation request (which quarantines the local license immediately), process it on the portal, then use a fresh offline challenge for the replacement installation. Challenges expire after 15 minutes. If either identity file is lost, contact support for purchase verification and an authorized re-issue; do not generate replacement identity files expecting them to unlock the old license. Old offline files cannot be remotely revoked. Recovery and offline import remain available without a valid paid entitlement.

Older ODIN releases do not enforce paid device binding. Roll out the new ODIN verifier before enabling bound new-purchase issuance on the portal; keep existing purchases in legacy mode unless explicitly converted.

Shared controls

  • All backup and restore actions require a superadmin.
  • Candidates are schema-allowlisted, restored for validation, and addressed by SHA-256.
  • Restore is offline: stop all ODIN API and worker roles before applying.
  • Record timings, size/hash, operator, outcome, recovery, and expiry—never row contents.

Use make test-database-parity CANDIDATE_PYTHON=python3.11 for measured HTML evidence.

SQLite

Backup

  1. Confirm free space (at least twice database size or 16 MiB).
  2. Create from System or POST /api/backups.
  3. Run:
make verify-backup DATABASE_URL=sqlite:////data/odin.db BACKUP_NAME=latest PYTHON=python3.11

Restore

  1. Upload through POST /api/backups/restore.
  2. Restart the bootstrap owner. ODIN locks, checkpoints WAL, journals a current rollback, and atomically swaps.
  3. Migrations and seed work run before finalization; failures and interrupted provisional restores roll back automatically.
  4. Verify readiness, login, inventory, jobs, and RBAC before reopening.

SQLite automatic backups and integrity checks

The supervised db_guardian process runs these on single-container SQLite installs.

  • Integrity check: read-only, every 5 minutes. A failure raises a critical alert and shows "database_integrity": {"status": "failed"} on /health until a check passes. ODIN never repairs the database.
  • Other states: pending (no check finished yet), retrying (one or two checks couldn't finish; overall status stays ok), unavailable (three in a row couldn't finish), stale (checks have stopped).
  • Backup: one verified odin_backup_*.db a day. It checks the live database first, restore-tests the result on a throwaway copy, and only then gives it that name and prunes.
  • Disk: a run needs room for two full copies plus 128 MiB. If not, it alerts, keeps every backup and tries again hourly. Backups are never pruned to make room.
  • Backups on /health: database_backup shows a state (pending, ok, failed, overdue, stale) and the time of the last good backup. It never changes the top-level status.
  • Missed backups: no verified backup for 26 hours raises "Backup missed", on the phone channels too. If db_guardian stops or won't start, report_runner raises the alert. These alerts ignore quiet hours, both the system's and a phone's own, so they can arrive at night. On a disk with no room at all, only /health can show it.
  • Retention: 7 daily and 4 weekly. Only files with a .receipt.json are pruned. A damaged database gets no new backup and nothing is pruned.
  • Limits: these backups share a disk with the live database, and a page that is out of date but self-consistent can pass the check.

SQLite off-server copies

ops/offsite_backup/odin-offsite-backup.mjs runs on a separate machine, pulls the newest verified backup over SSH and writes it encrypted to the NAS, so plaintext never reaches a disk there. It reads every stored copy back before pruning, keeps 7 daily and 4 weekly among the good ones, and never deletes a bad one. A run with no progress for two minutes is stopped and recorded. ODIN alerts if no copy is confirmed for 36 hours from installation. Installing it needs the owner's go and changes two machines, including trusting the ODIN host's key first; the steps are in the Markdown runbook. Keep a second copy of the key: without it no copy can be restored. Never paste it into a chat, ticket or log.

Database failed its integrity check

This is damage in the database file, so rolling back the release won't help. A running ODIN keeps working until it restarts, then refuses to start. Older releases say "Media ownership database integrity differs".

  1. Copy first: stop the container, copy odin.db with any -wal and -shm files to a new private directory, and record its SHA-256.
  2. Find what is damaged, on a second copy.
  3. Compare a repair with restoring the newest good backup, with the owner. Nothing touches live data without the owner's yes.
  4. Test on a copy with DATABASE_URL=sqlite:////path/to/copy/odin.db ODIN_DB_ROLE=bootstrap python3 -m scripts.bootstrap_database, from /app/backend in the same image. It has to exit 0.
  5. With the owner's yes, check the live file still matches, then apply exactly what you tested.
  6. Confirm /health shows ok and a new backup appears.

POST /api/backups/restore can refuse on a damaged database, because its safety copy can fail. Use the offline steps then.

PostgreSQL identities

  • odin_admin: initialization-only superuser, secret visible only to PostgreSQL.
  • odin: application owner, no superuser/createdb/createrole.
  • odin_maintenance: non-superuser validation identity with CREATEDB; secret visible only to the bootstrap-owner API.
DATABASE_URL=postgresql://odin@postgres:5432/odin
DATABASE_MAINTENANCE_URL=postgresql://odin_maintenance@postgres:5432/postgres

PostgreSQL backup

  1. Create from System or POST /api/backups.
  2. ODIN dumps only the canonical public object allowlist and strips ownership, privileges, and comments.
  3. ODIN restores into a disposable database and validates exact schema before publication.
  4. Run make verify-backup with the credentialless application URL and mounted application/maintenance password files.

PostgreSQL restore

  1. Upload a canonical .dump and record candidate_sha256.
  2. Stop every ODIN role; leave PostgreSQL running. Isolate the target database network until verification completes; session checks are point-in-time and network quiescence is the operator's continuous exclusion boundary.
  3. Set ODIN_POSTGRES_RESTORE_ACKNOWLEDGEMENT to the exact SHA-256 and start only the bootstrap owner.
  4. ODIN locks, refuses all other target sessions, checks dependencies, then creates a current verified rollback.
  5. The allowlisted restore is transactional and object-scoped; bootstrap, validation, and auditing occur under the lock.
  6. Failures roll back immediately. A next start recovers any restore_in_progress interruption before serving.
  7. Remove the acknowledgement, start other roles, and verify readiness, login, RBAC, WebSocket, background writes, printers, and jobs.

Failure rules

  • Never edit a pending manifest to force startup.
  • Never put passwords in PostgreSQL URLs or PGPASSWORD.
  • Never bypass session refusal, checksums, TOC allowlists, or disposable validation.
  • If rollback fails, keep ODIN stopped, preserve evidence, and escalate—do not improvise restore flags.
